Concepts · deep dive

How the pieces fit together

Four techniques do the real work in a computer-vision pipeline — tracking, projective geometry, embeddings, and the metrics that tell you whether any of it worked. This starts with a map of how they compose, then takes each one apart.

§01

The map

Individually each technique is a self-contained idea. What makes a pipeline is the contract between them — what each one consumes, what it emits, and what the next stage is entitled to assume. Click any box to see its role, its input and output, and how it can fail.

Every one of those "assumes" is a place a silent bug lives. The tracker's is the sharpest: downstream code treats tracker_id as ground truth, but an ID switch silently transfers one player's history to another, and nothing in the data marks it.

§02

Tracking — prediction, then matching

A tracker answers one question per frame: which of these new boxes is which of my existing objects? It solves it in two steps, and it's worth separating them because they fail differently.

Step 1 — the Kalman filter predicts

Before comparing anything, the tracker guesses where each object should be now, based on where it was and how fast it was moving. This matters more than it sounds. A player moving 40 px per frame with a 34 px-wide box produces boxes in consecutive frames that don't overlap at all — match on last position and you get zero IoU and a broken track. Match against the prediction and it's easy.

The filter maintains a belief about the object's state — position and velocity — plus an uncertainty about that belief. Each frame it does two things: predict (move the belief forward, uncertainty grows) and correct (pull the belief toward the new measurement, uncertainty shrinks). How hard it pulls depends on which it trusts more.

The five equations

Predict — move the state forward by the motion model F, and grow the uncertainty by the process noise Q:

x⁻ = F x P⁻ = F P Fᵀ + Q

Correct — weigh prediction against measurement z. K is the Kalman gain; when measurement noise R is large, K → 0 and the filter ignores the measurement:

K = P⁻ Hᵀ (H P⁻ Hᵀ + R)⁻¹ x = x⁻ + K (z − H x⁻) P = (I − K H) P⁻

For 2-D box tracking the state is typically [x, y, aspect, height, ẋ, ẏ, ȧ, ḣ] — position plus velocity — and F is constant-velocity: new position = old position + velocity.

Why it matters practically: an unmatched track keeps predicting with P growing every frame. That's "coasting", and lost_track_buffer caps how long before the track is deleted.

Step 2 — the Hungarian algorithm matches

Now you have N predictions and M detections, and a cost for every pair (usually 1 − IoU). You need an assignment where each track gets at most one detection and vice versa, minimising total cost.

The tempting approach is greedy: take the cheapest pair, remove both, repeat. It's simple and often right — but it can be provably worse, because taking a locally cheap pair can force an expensive one later. The Hungarian algorithm finds the globally optimal assignment in O(n³).

Where ByteTrack fits

Both steps above are generic. ByteTrack's addition is to run the matching twice: once with high-confidence detections, then again using the discarded low-confidence ones against whatever tracks are still unmatched. A weak detection is untrustworthy alone but convincing when it lands exactly where a track predicted — which is what carries identities through occlusion.

§03

Projective geometry — pixels to metres

A camera flattens 3-D into 2-D and destroys scale doing it. But if everything you care about lies on one plane — a pitch, a road, a table — the damage is exactly invertible with a single 3×3 matrix.

Homogeneous coordinates, and why they exist

The trick that makes this work is representing a 2-D point with three numbers: (x, y) becomes (x, y, 1), and any scalar multiple means the same point — (2x, 2y, 2) is the same as (x, y, 1). To recover ordinary coordinates you divide by the third component.

Why bother? Because that division is where perspective comes from. A linear matrix multiply cannot produce foreshortening — but a matrix multiply followed by a divide can. Homogeneous coordinates let a single matrix express translation, rotation, scaling and perspective, all composable by multiplication.

⎡x'⎤ ⎡h₁₁ h₁₂ h₁₃⎤ ⎡x⎤ ⎢y'⎥ = ⎢h₂₁ h₂₂ h₂₃⎥ ⎢y⎥ X = x'/w' Y = y'/w' ⎣w'⎦ ⎣h₃₁ h₃₂ 1 ⎦ ⎣1⎦ ← the divide creates perspective

Scale is arbitrary, so fixing h₃₃ = 1 leaves 8 unknowns. Each point correspondence gives two equations, so 4 points suffice — that's the whole reason the number is four.

Deriving the linear system (DLT)

Start from the mapping for one correspondence (x,y) → (X,Y):

X = (h₁₁x + h₁₂y + h₁₃) / (h₃₁x + h₃₂y + 1)

That's non-linear in the unknowns because they appear in the denominator. Multiply both sides by the denominator and everything becomes linear:

X(h₃₁x + h₃₂y + 1) = h₁₁x + h₁₂y + h₁₃ h₁₁x + h₁₂y + h₁₃ − h₃₁xX − h₃₂yX = X ← linear in h h₂₁x + h₂₂y + h₂₃ − h₃₁xY − h₃₂yY = Y

Four correspondences stack into an 8×8 system A h = b, solved by Gaussian elimination. That's the Direct Linear Transform, and it's what cv2.findHomography does — with robust estimation (RANSAC) layered on when you supply more than four points.

What breaks it: three collinear points, or four points bunched into a small image region. Both make A ill-conditioned. The failure is numerical, not obvious — you get a matrix, it just isn't the right one.

§04

Embeddings — meaning as coordinates

An embedding is a vector that represents something, arranged so that distance means similarity. Two photos of the same kit land near each other; a photo of a different kit lands far away. Nothing about the vector is human-readable — the geometry is the whole point.

Your pipeline already uses two kinds, and the difference is instructive:

HSV colour histogramSigLIP / CLIP embedding
Made byCounting pixels into binsA trained vision transformer
EncodesColour distribution, nothing elseSemantic content
CostMicroseconds, CPUA forward pass, GPU
Fails whenLighting shifts the coloursRarely — but it's ~100× slower

The histogram is a hand-designed embedding: a human decided that colour distribution is what matters. SigLIP learned its space from data. Same interface — image in, vector out, distance means similarity — completely different provenance.

Why cosine similarity, not Euclidean distance

Embeddings are usually compared by the angle between vectors rather than the distance between their tips. Normalise every vector to unit length and the dot product is the cosine of the angle: 1 means identical direction, 0 unrelated, −1 opposite.

The reason is that magnitude tends to encode things you don't care about — image brightness, how confidently the model fired — while direction encodes what it is. Two photos of the same player under different lighting can have quite different vector lengths but nearly identical direction.

Where this goes next

Zero-shot classification is this exact mechanism: embed the image, embed the label names as text, return whichever label sits closest. No training, no examples. It's the foundation of the wildlife/VLM project later in the roadmap, and it's why "just describe the classes in English" became a viable first move in 2026.

§05

Detection metrics — what mAP actually measures

You've been quoting mAP50 and mAP50-95. Here's what's inside them, because the construction explains several otherwise-confusing behaviours.

Step 1 — a prediction is correct if it overlaps enough

IoU (intersection over union) is the overlap ratio between a predicted box and a ground-truth box: shared area divided by combined area. 1.0 is perfect, 0 is disjoint. A prediction counts as a true positive if its IoU with an unclaimed ground-truth box exceeds a threshold — and which threshold is a choice, not a fact.

Step 2 — sweep the confidence threshold

Sort predictions by confidence, walk down the list, and after each one recompute precision (of what I've predicted, what fraction is right?) and recall (of what exists, what fraction have I found?). Plotting precision against recall traces a curve, and average precision is the area under it.

This is why AP is a better summary than accuracy: it evaluates the model at every operating point at once, rather than at one arbitrarily chosen confidence cutoff.

Step 3 — the two numbers you keep seeing

MetricHow it's computedWhat it tells you
mAP50AP at IoU ≥ 0.50, averaged over classesDid you find the objects? Forgiving about box tightness.
mAP50-95AP averaged over IoU 0.50, 0.55 … 0.95Did you find them and localise them precisely? Always lower.

The m is "mean over classes" — which is where the most common misreading lives. A model can post a healthy mAP while being useless at the class you actually care about, because a strong majority class carries the average. Your VisDrone run is a live example: 0.280 overall, but that average includes a `ball`-like small-object class performing far worse than the headline suggests.

Read per-class, always

For the soccer project this is not a nicety. Ball detection will be dramatically worse than player detection — 10 px versus 200 px — and a single averaged number will hide exactly the failure you most need to see. Report per-class AP, and never let the ball's score disappear inside a mean.

§06

Putting it back together

Return to the map at the top and the composition should read differently now:

  • The detector is a learned function producing per-frame boxes with no memory.
  • The tracker adds memory using a motion model plus an optimal assignment — neither of which is learned.
  • The embedder turns appearance into geometry so that clustering becomes possible without labels.
  • The homography undoes the camera's projection, on the one plane where that's invertible, converting pixels into physical units.
  • The metrics are how you find out whether any of the above is working — and are themselves a modelling choice, not a fact.

Two stages learned; three not. The most common failures in this pipeline aren't model failures — they're contract violations between stages: a class index meaning something different than assumed, a calibration quad placed by eye, a metric that can't distinguish the two hypotheses you care about.
