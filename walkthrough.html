Project 03 · Design document

Soccer analytics from broadcast video

An architecture walkthrough of the six-stage pipeline that turns a match clip into tracked players, team assignments, a tactical minimap and per-player distance — written before the code, so the failure modes are chosen rather than discovered.

Input 1080p+ broadcast clip Output annotated video · minimap · stats Stack YOLO26 · ByteTrack · OpenCV · scikit-learn Runs on single GPU

Why a design document at all: the previous project in this series ran end‑to‑end without a single exception and was still wrong in five places. Every one of those bugs was silent — plausible numbers, no stack trace. Deciding the data contracts and failure modes up front is the actual fix for that pattern, not more careful coding.

§00

Control flow: why two passes

k-means must see data before it can assign anything, and the team clusters aren't known until players have been observed. So the video is read twice: once to fit, once to render.

§01

Detection — finding players in a single frame

The detector looks at one frame in isolation and returns boxes. It has no memory: nothing in its output says "this is the same player as last frame". That's the tracker's job, and keeping the two responsibilities separate is what makes the pipeline debuggable.

Modern YOLO differs from the YOLOv5 generation in two ways worth knowing. It's anchor-free — it predicts box geometry directly rather than as offsets from predefined anchor shapes, which removes a set of dataset-specific hyperparameters. And the newest versions are NMS-free: trained with one-to-one label assignment so they emit one box per object, removing the non-maximum-suppression cleanup step from inference entirely. Fewer moving parts, faster on edge hardware.

For each detection you get four numbers for the box, a confidence, and a class index. That last one is where the trap lives.

The trap · costs you a whole run

A class index is only meaningful relative to the model that produced it. In COCO, index 0 is person. In a soccer-specific model the classes are typically ball, goalkeeper, player, referee — index 0 is the ball.

The existing scaffold for this project contains the line person_class = 0. That is correct for the pretrained COCO model it currently uses, and becomes silently, catastrophically wrong the moment a fine-tuned soccer model is loaded — the pipeline would track the ball as if it were a squad of players and quietly produce a full set of plausible-looking statistics.

This exact mistake invalidated the previous project's entire evaluation: a COCO model was scored against a drone dataset by index, so its airplane predictions were graded against van boxes and train against tricycle. The resulting number looked like a real measurement and meant nothing.

The fix, in one rule: resolve classes by name, never by literal index.

PLAYER_NAMES = {"player", "person", "goalkeeper"} def player_class_ids(model): return [i for i, n in model.names.items() if str(n).lower() in PLAYER_NAMES]

The same function then works unchanged across the COCO baseline and every fine-tuned checkpoint, and it fails loudly — no matching names — rather than quietly detecting the wrong thing.

§02

Tracking — keeping identity across frames

Detection gives you boxes per frame. Tracking answers the harder question: which box in this frame is the same object as which box in the last frame? This is the data association problem, and every derived statistic depends on getting it right. Distance covered is meaningless if a player's identity changes halfway through the clip.

The standard approach has two parts. A Kalman filter predicts where each existing track should appear next, using a constant-velocity motion model — cheap, and good enough over the tens of milliseconds between frames. Then the Hungarian algorithm optimally matches predictions to new detections, scored by IoU (box overlap).

ByteTrack's contribution is smaller and cleverer than it sounds: don't throw away low-confidence detections. Conventional trackers discard everything below a threshold, which is exactly wrong during occlusion — a partially hidden player still produces a weak detection, and discarding it breaks the track. ByteTrack associates high-confidence boxes first, then runs a second association round using the leftovers to rescue tracks that would otherwise be lost.

The Kalman predict / update cycle

State x holds position and velocity; P is its uncertainty. Between frames, predict:

x⁻ = F x (constant-velocity motion) P⁻ = F P Fᵀ + Q (uncertainty grows)

When a detection z is matched, correct toward it — weighted by how much you trust the measurement versus the prediction:

K = P⁻ Hᵀ (H P⁻ Hᵀ + R)⁻¹ (Kalman gain) x = x⁻ + K (z − H x⁻) P = (I − K H) P⁻

Practical consequence: an unmatched track keeps coasting on prediction alone with P growing each frame. lost_track_buffer caps how many frames it may coast before the track is deleted.

The characteristic failure is the ID switch — two players cross, and the tracker swaps their identities. It's visible in output (a jersey number jumping between people) and measurable, but only against ground-truth tracking annotations using metrics like MOTA and IDF1. Without those labels you can't quantify it, and it's more honest to say so than to invent a proxy.

Metric discipline

In the previous project the tracker sweep logged only "number of unique IDs". That number rises both when tracks fragment and when a lower threshold legitimately detects more objects — two opposite explanations predicting the same movement, so the metric could not answer its own question.

Logging detections per frame and mean track length alongside it separates them: IDs up with detections up and track length steady means more real objects; IDs up with track length down means fragmentation. Decide what each hypothesis predicts before collecting the number.

§03

Team assignment — unsupervised, and free

Nobody labels which team each player belongs to. You don't need them to. Kit colour dominates the appearance of a player crop, so if you embed each crop into a vector space, the crops form two obvious clusters. k-means with k=2 separates them in milliseconds, with no annotation and no training.

Two embedders, a deliberate trade-off:

EmbedderWhat it isCostBest when
HSV histogram Colour histogram of the torso region — upper-centre of the crop, which is mostly shirt and avoids grass at the edges Microseconds, CPU Kits are colour-distinct and lighting is even
SigLIP embedding A vision-transformer's learned representation — semantic, not just colour GPU, ~100× slower Shadows, floodlights, mixed lighting across the pitch

Start with the histogram. It is genuinely good enough for most broadcast footage, and the point of choosing the cheap thing first is that you find out whether you need the expensive thing.

This is the honest failure to document rather than hide: two goalkeepers in distinct kits and a referee in a fifth colour cannot be represented by two clusters. You can raise k and keep the two largest clusters, or detect goalkeepers as a separate class in the detector — which a fine-tuned soccer model already does.

§04

Homography — the geometry that makes it real

This is the centre of the project, and the only part that is pure classical geometry with no learning involved.

Pixel distances are meaningless. Two players ten metres apart near the camera span hundreds of pixels; the same ten metres at the far touchline spans a few dozen. Any statistic computed in pixel space — distance covered, speed, spacing — is not just imprecise but systematically wrong, and wrong by a different factor at every depth.

The fix rests on one fact: a football pitch is a plane. Any two views of a plane are related by a single 3×3 matrix — a homography. Find that matrix once and you can convert any point on the pitch surface from pixels to metres.

It has eight degrees of freedom, so four point correspondences are enough: each gives you two equations, four gives eight. Corner flags, penalty-box corners, the centre spot and the halfway-line intersections are all landmarks whose real-world coordinates you already know.

Free ground truth

Here is the structural advantage this project has over the last one: a pitch is 105 × 68 metres by regulation. The real-world coordinates aren't estimated, they're specified by the laws of the game.

The previous project had no such reference. Its calibration quad was placed by eye and assumed 30 m of road depth where the true span was ~250 m — so every speed was under-reported by roughly 8×, and the pipeline reported 55 km/h traffic on a free-flowing motorway without complaint. Distance error propagates linearly into speed. Here, that entire class of error is off the table for free.

Drag the corner markers below. They start on the true pitch corners, so the mapping is exact and the error reads zero. Move one and watch the reconstruction degrade — this is precisely what a mis-calibrated pipeline does, silently.

The homography matrix and the DLT solve

In homogeneous coordinates the mapping is a single matrix multiply, with the result divided through by the third component — that division is what produces perspective:

⎡x'⎤ ⎡h₁₁ h₁₂ h₁₃⎤ ⎡x⎤ ⎢y'⎥ = ⎢h₂₁ h₂₂ h₂₃⎥ ⎢y⎥ ⎣w'⎦ ⎣h₃₁ h₃₂ 1 ⎦ ⎣1⎦ X = x'/w' Y = y'/w'

Scale is arbitrary, so fixing h₃₃ = 1 leaves 8 unknowns. Expanding and clearing the denominator for one correspondence (x,y) → (X,Y) gives two linear equations:

h₁₁x + h₁₂y + h₁₃ − h₃₁xX − h₃₂yX = X h₂₁x + h₂₂y + h₂₃ − h₃₁xY − h₃₂yY = Y

Four correspondences stack into an 8×8 system solved directly by Gaussian elimination — this is the Direct Linear Transform, and it is what cv2.findHomography does (with robustness machinery on top when you supply more than four points).

What breaks it: three collinear points, or four points clustered in a small image region. Both make the system ill-conditioned, and the failure is numerical rather than obvious — you get a matrix, it just isn't the right one. Spread correspondences as widely across the frame as possible.

One assumption to keep in mind

A homography maps a plane. It is valid only for points actually on the pitch surface — which is why player positions are taken from the bottom-centre of the box, the feet. Use the box centre and you are mapping a point roughly a metre above the plane, and the reconstruction is wrong by an amount that grows with distance from the camera. A ball in flight is off-plane by definition; its map position is only meaningful when it's on the ground.

§05

The ball — the genuinely hard part

Expect this to be the part that doesn't work first time. A football in broadcast footage is small, fast, frequently occluded by players, and motion-blurred into an ellipse whenever it's kicked with intent.

The core difficulty is scale. Inference typically runs at 640 px, so a 4K frame is downscaled by a factor of six before the detector sees anything:

Three approaches, in increasing order of effort:

  1. Raise inference resolution. The cheapest intervention and often sufficient. In the previous project, moving from 640 to 1280 px raised detections per frame from 3.10 to 4.88 — and, more interestingly, raised mean track length from 47.8 to 81.3 frames while reducing the unique ID count. More detections plus fewer IDs plus longer tracks means the extra resolution didn't merely find more objects, it stopped the tracker losing the ones it already had.
  2. Tiled inference (SAHI). Slice the frame into overlapping tiles, run the detector on each at full resolution, merge the results. Small objects are effectively magnified. Costs several forward passes per frame.
  3. Motion priors. A ball follows smooth ballistic arcs. A Kalman filter tuned for that motion can interpolate through gaps where the detector loses it entirely — accepting interpolated positions as a legitimate output, clearly labelled as such.

A fine-tuned model helps here too: ball as an explicit class, trained on footage where the ball is small, beats a COCO model's sports ball class trained mostly on large, centred, unblurred examples.

§06

Statistics — easy to compute, easy to compute meaninglessly

Once positions are in metres, the statistics are arithmetic. The difficulty is entirely in whether they mean anything.

StatisticComputationHow it goes wrong
Distance covered Sum of per-frame displacement per tracker_id An ID switch teleports a player across the pitch and adds tens of metres in one frame
Speed Displacement ÷ elapsed time, over a short window Per-frame differencing amplifies jitter — needs a window, and a sanity check against plausible human speed
Possession Nearest player to the ball, aggregated by team Flickers wildly frame to frame when two players contest; needs hysteresis, not raw nearest-neighbour
Team shape Convex hull or centroid spread per team One misassigned goalkeeper drags the centroid the length of the pitch

The distance calculation in the scaffold already carries a guard for exactly the first failure:

if step < 2.0: # metres in one frame distance_m[tid] += step

A player cannot cover two metres in a single frame at 25 fps — that would be 180 km/h — so a larger jump is definitionally an ID switch rather than movement, and is discarded. This is a heuristic, and a defensible one, but it must be stated: it silently drops real motion in dropped-frame footage, and it makes reported distance a lower bound rather than a measurement. Undocumented, it's the kind of thing that quietly makes a number 10% wrong forever.

§08

Design decisions and their costs

Every one of these is a real trade-off in the current scaffold, with a real price attached.

Two passes over the video

k-means cannot predict before it has been fitted, so the clip is read twice. The cost is doubled decode time and detection being run twice on the fitting frames. The alternative — fit on the first N frames while buffering them, then render — trades memory for I/O and complicates the code. Two passes is the right call for offline analysis and the wrong one for a live stream, where you'd instead fit on a rolling window and accept that early frames use a provisional model.

Re-embedding every player every frame

The scaffold calls teams.predict() on every crop in every frame. With the histogram embedder that's cheap enough to ignore. With SigLIP it dominates runtime — a vision transformer forward pass per player per frame, ~250 redundant inferences per second of footage.

The fix is straightforward and worth building in from the start: a player's team does not change, so classify once per tracker_id and cache. This also fixes the flicker failure mode above, since a cached assignment can't oscillate. Two problems, one change.

Overloading class_id to carry team

The scaffold writes team assignments into the class_id field so the annotator colours boxes by team. It works, and it costs you the original detection class — after that line you can no longer tell a player from a goalkeeper, because the field that knew has been overwritten. Acceptable when the only downstream consumer is the renderer; actively harmful the moment anything else needs the real class. Carry team in a separate array.

Histogram before SigLIP

Start with the cheap embedder specifically so you learn whether the expensive one is necessary. Reaching for the transformer first means never finding out, and paying for it forever.

What "done" looks like

Written now, before any training run, so success criteria can't be quietly retrofitted to whatever the numbers turn out to be.

Distance statsWithin a plausible range for 90 minutes (~10–12 km)Extrapolate from the clip; sanity-check against published figures

That last row is the pattern worth internalising, and it's the one that would have caught every silent bug in the previous project: check the output against something you know independently of the code. Motorways are not 55 km/h zones. Drone datasets do not contain boats. Footballers cover about 10 km a match. None of those facts come from the pipeline, which is exactly what makes them useful for testing it.
